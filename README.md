# Поиск уязвимостей по продуктам и версиям

Консольный инструмент и база данных по двум фидам:

* **фид уязвимостей** (`data/vulnerabilities.json`): производитель, продукт, идентификатор статьи (KLA), короткое описание, дата публикации, первая уязвимая версия, первая исправленная версия;
* **фид версий** (`data/versions.json`): производитель, продукт, версия.

Инструмент умеет:

1. по названию продукта вывести **версию без уязвимостей**;
2. по названию продукта и версии вывести **информацию об уязвимостях**.

Только стандартная библиотека Python (SQLite встроен), устанавливать ничего не нужно.

## Требования

Python **3.8 или новее**.

## Быстрый старт

Сначала создайте базу из JSON-файлов в папке `data/` (команда выполняется один раз и занимает долю секунды):

```
py vulndb.py load
```

После этого можно пользоваться:

```
py vulndb.py safe "Apache Tomcat"
py vulndb.py check "Apache Tomcat" 9.0.50
```

Базу можно пересоздать в любой момент той же командой `load`. Файл `vulns.db` не хранится в репозитории (он в `.gitignore`), потому что целиком воспроизводится из `data/`; в zip-архиве с решением готовая база уже лежит, и там `load` можно пропустить.

На Windows, если команда `py` не находится, используйте `python`; на macOS и Linux — `python3`.

## Команды

|Команда|Что делает|
|-|-|
|`py vulndb.py load`|создаёт базу заново и загружает в неё оба фида|
|`py vulndb.py safe ПРОДУКТ`|выводит версию без известных уязвимостей (самую новую из безопасных)|
|`py vulndb.py safe ПРОДУКТ --all`|выводит все версии без известных уязвимостей|
|`py vulndb.py check ПРОДУКТ ВЕРСИЯ`|выводит уязвимости указанной версии|
|`py vulndb.py products`|список продуктов, которые есть в базе|
|`py vulndb.py validate`|проверка целостности базы|

Общие замечания:

* название продукта можно писать в кавычках (`"Apache Tomcat"`) и без них (`Apache Tomcat`); в `check` версия всегда последний аргумент;
* название ищется **точно**, без учёта регистра: `apache tomcat` найдёт `Apache Tomcat`, а `VLC media player` не найдёт `VLC media player (MSI installer)`;
* `--vendor ВЕНДОР` нужен только если название продукта есть у нескольких вендоров (в текущих данных таких нет);
* `--db ФАЙЛ` указывает другую базу (по умолчанию `vulns.db` рядом с программой), запускать можно из любой папки;
* `py vulndb.py ПОДКОМАНДА --help` показывает справку, `py -m vulndb ...` работает так же, как `py vulndb.py ...`.

### Примеры

Версия без уязвимостей:

```
$ py vulndb.py safe "KeePass Password Safe"
Продукт: KeePass Password Safe (вендор: Dominik Reichl)
Версия без известных уязвимостей: 2.57.1
(всего таких версий: 44 из 52; полный список: добавьте --all)
```

Уязвимости версии:

```
$ py vulndb.py check "Foxit Reader Enterprise" 2024.2.3.25184
Продукт: Foxit Reader Enterprise (вендор: Foxit Corporation)
Версия: 2024.2.3.25184
Найдено уязвимостей: 2

1. KLA78282 (2024-12-17)
   Multiple vulnerabilities in Foxit Reader
   Первая уязвимая версия: 0
   Исправлено в: 2024.4.0.27683

2. KLA74565 (2024-09-26)
   PE vulnerability in Foxit Reader
   Первая уязвимая версия: 0
   Исправлено в: 2024.3.0.26795

Ближайшая версия без известных уязвимостей: 2024.4.0.27683
```

Продукт, у которого безопасных версий в базе нет:

```
$ py vulndb.py safe "Oracle VirtualBox"
Продукт: Oracle VirtualBox (вендор: Oracle Corporation)
Версий без известных уязвимостей в базе нет (проверено версий: 14).
Самая новая известная версия: 7.1.4 (уязвима).
Ближайшая версия без известных уязвимостей: 7.1.6 (в базе такой версии нет).
```

Ошибки (сообщение идёт в поток ошибок):

```
$ py vulndb.py safe Tomcta
Ошибка: продукт 'Tomcta' не найден. Возможно, вы имели в виду: Apache Tomcat

$ py vulndb.py check "Apache Tomcat" 9.0.x
Ошибка: некорректная версия '9.0.x': ожидаются числа, разделённые точками (например, 2.4.1)
```

### Коды возврата

|Код|Когда|
|-|-|
|0|успех|
|1|продукт не найден (или название неоднозначно), база не найдена или не читается, загрузка не удалась, при `validate` найдены ошибки|
|2|неверный формат версии или неверные аргументы командной строки|

Команды `safe`, `check`, `products` и `validate` базу только читают и никогда не изменяют; если файла базы нет, они его не создают, а подсказывают выполнить `load`.

## Как определяется уязвимость

Каждая строка фида уязвимостей задаёт **диапазон**: от первой уязвимой версии (включительно) до первой исправленной (не включая):

> версия **v** продукта **P** уязвима по записи, если `start ≤ v < fixed`.
> Версия безопасна, если по продукту нет ни одной записи, под которую она попадает.

Версия сравнивается **как набор чисел**, а не как строка: `9.0.10` новее `9.0.9` (как строки было бы наоборот), недостающие компоненты считаются нулями (`128.3` = `128.3.0`).

## Проектирование базы данных

Используется SQLite, схема описана в [`vulndb/schema.sql`](vulndb/schema.sql).

```
vendors ──< products ──< versions               фид версий
               │
               └──< vuln_ranges >── advisories   фид уязвимостей
```

|Таблица|Поля|Ключи и ограничения|
|-|-|-|
|`vendors`|`id`, `name`|`name` уникально и не пусто|
|`products`|`id`, `vendor_id`, `name`|`UNIQUE(vendor_id, name)`, сравнение имён без учёта регистра|
|`versions`|`id`, `product_id`, `version`, `version_key`|`UNIQUE(product_id, version)`|
|`advisories`|`kla_id`, `description`, `publish_date`|`kla_id` — первичный ключ вида `KLA12345`; дата — существующая дата `ГГГГ-ММ-ДД`|
|`vuln_ranges`|`id`, `kla_id`, `product_id`, `start_version`, `start_key`, `fixed_version`, `fixed_key`|`UNIQUE(kla_id, product_id, start_version, fixed_version)`, `CHECK(start_key <= fixed_key)`|

Куда попадают поля фидов:

|Поле фида|Таблица и поле|
|-|-|
|производитель (оба фида)|`vendors.name`|
|продукт (оба фида)|`products.name`|
|версия (фид версий)|`versions.version`|
|идентификатор статьи|`advisories.kla_id`|
|короткое описание|`advisories.description`|
|дата публикации|`advisories.publish_date`|
|первая уязвимая версия|`vuln_ranges.start_version`|
|первая исправленная версия|`vuln_ranges.fixed_version`|

Ключевые решения:

* **Бюллетень и диапазон — разные сущности.** В фиде уязвимостей 135 строк, но только 105 уникальных `KLA_id`: один бюллетень встречается в нескольких строках (по одной на продукт или на ветку продукта), а описание и дата у него общие. Поэтому они хранятся один раз в `advisories`, а каждая строка фида — это диапазон в `vuln_ranges`. Так нет дублирования и невозможно получить два разных описания одного бюллетеня.
* **Ключ сортировки версий** (`version_key`, `start_key`, `fixed_key`). SQLite не умеет сравнивать версии, поэтому рядом с исходным текстом хранится строка, у которой обычное строковое сравнение совпадает с числовым сравнением версий: версия разбирается в числа, дополняется нулями до 6 компонентов, каждое число дополняется нулями слева до 10 цифр (`9.0.10` → `0000000009.0000000000.0000000010.0000000000.0000000000.0000000000`). Благодаря этому уязвимость проверяется чистым SQL: `start_key <= version_key AND version_key < fixed_key`. Ключи всегда считает загрузчик одной и той же функцией `make_key`, а команда `validate` перепроверяет их соответствие тексту.
* **Внешние ключи включены** при каждом подключении, на нужные поля созданы индексы, версия схемы хранится в `PRAGMA user_version`.
* **Загрузка безопасна.** Она выполняется в одной транзакции, база строится во временном файле и подменяет старую только при полном успехе. Любая ошибка в данных (нет поля, неверная версия или дата, у одного `KLA_id` разные описания) даёт понятное сообщение с номером записи, а прежняя база остаётся нетронутой.

## Допущения и особенности данных

|Что|Как реализовано|
|-|-|
|«Версия без уязвимостей»|самая новая версия из справочника, не попавшая ни в один диапазон; все такие версии показывает `--all`|
|Версия, которой нет в справочнике|всё равно проверяется по диапазонам, с примечанием|
|Бюллетень с несколькими диапазонами|выводится **один раз**, в нём перечислены все исправленные версии|
|Правила берутся буквально|если у бюллетеня несколько строк с началом `0` (по одной на ветку, как у PostgreSQL), их объединение закрывает всё от нуля до самой большой исправленной версии: информации о ветках в фиде нет, и она не домысливается|
|«Ближайшая версия без уязвимостей»|наименьшая версия не ниже проверяемой, под которую не попадает ни одно правило продукта; в справочнике её может не быть|
|Пустой диапазон `128 → 128.0` (`KLA70478`, Thunderbird)|`128` и `128.0` — одна версия, поэтому диапазон пуст; запись сохраняется, при загрузке выводится предупреждение, уязвимой она не делает ни одну версию|
|Исправленные версии вне справочника|у 17 правил исправленной версии нет в фиде версий (сравнение по значению: `128.3` и `128.3.0` — одна версия); на корректность это не влияет|
|Oracle VirtualBox|все 14 известных версий уязвимы, `safe` об этом честно сообщает|

Все такие наблюдения видны в отчёте `py vulndb.py validate` (ошибок нет, одно предупреждение и три замечания).

## Структура проекта

```
vulndb.py            точка входа: py vulndb.py <команда>
vulns.db             база (создаётся командой load; в репозитории её нет)
data/                исходные фиды: versions.json, vulnerabilities.json
vulndb/
  schema.sql         схема базы данных
  versioning.py      разбор версий и ключ сортировки
  loader.py          загрузка фидов в базу
  validate.py        проверки целостности базы
  queries.py         запросы: безопасные версии и уязвимости версии
  cli.py             консольный интерфейс
  db.py, paths.py, console.py   подключение к SQLite, пути, вывод
tests/               тесты
```

## Тесты

```
py -m unittest -v
```

Тесты не затрагивают `vulns.db`: все они работают с временными базами. Что проверяется:

* разбор и сравнение версий, включая граничные случаи;
* ограничения схемы (внешние ключи, уникальность, форматы, диапазоны);
* загрузка настоящих фидов, каждая ошибка данных, атомарная замена базы;
* проверки целостности на намеренно испорченных базах;
* **сверка с независимым расчётом**: для всех 834 версий справочника результаты `safe` и `check` сравниваются с эталоном, посчитанным прямо из JSON обычным сравнением кортежей, без SQL и без общего с программой кода сравнения версий;
* консоль: все команды, коды возврата, запуск из другой папки, защита от старых кодировок консоли и от закрытого канала (`| head`).
